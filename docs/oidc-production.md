# OIDC 生产化与上线计划

## 目标与当前状态

目标是在明确支持范围后，将 Authx 作为生产 OIDC 身份提供方供多个应用接入。
当前实现仅用于本机开发、测试和受限的本地试运行，**未完成本文的上线门禁前，
不要对外开放**。
现有流程及限制见 [OIDC client demo](client-demo.md)。

本文件是待执行的工程和上线清单，不代表下列功能已经实现。每一步完成后应
记录变更、测试结果和负责人；失败项先修复再进入依赖它的步骤。生产操作必须
由部署负责人确认，不能使用开发账号、密钥或数据库。

当前需要特别注意：

- OAuth2/OIDC 路由始终挂载；正式部署必须显式提供 `AUTHX_ISSUER`、
  `AUTHX_OAUTH_SIGNING_SECRET` 和 `AUTHX_OIDC_PRIVATE_KEY_FILE`。对外开放前
  仍须完成本文的上线门禁。
- 默认 demo 的 ID Token RSA 密钥在进程启动时临时生成；受限本地生产模式
  可从文件加载固定密钥，但尚无轮换。OIDC access token 使用独立对称签名
  密钥，不由 JWKS 验证。
- 受限本地生产模式的 issuer 默认是 `https://authx.s`，可用 `AUTHX_ISSUER`
  覆盖；正式生产的 issuer、资源地址及密钥管理仍须单独设计。
- 当前 OIDC token endpoint 仅支持公开客户端 `none`，没有 OIDC refresh
  token 或全局注销；依赖的 token 实现也不支持机密客户端认证。

## 0. 确认范围和部署条件

**依赖：无。先完成决策，再按顺序实施；不得把下述待定项当成已获批准。**

- 定位是超级个人开发者，安全优先、简洁设计。目标是分离管理员和开发者
  角色：管理员手动授权已有用户成为开发者；开发者通过独立控制台管理
  自己的客户端，一人可以兼具两种角色，客户端注册无需审核。当前代码
  尚未实现开发者角色、控制台和归属，详见
  [OIDC 客户端管理](oidc-client-management.md)。首批接入
  服务端 Web 应用和浏览器插件；本地试运行暂用公开客户端，正式生产的
  服务端 Web 应用需要机密客户端认证。初期采用单实例和受控密钥文件。
- 实现方向：继续以 Authx 为 OIDC Provider，评估并补齐现有实现；当前依赖
  不支持机密客户端认证，需要先验证扩展或替换相关协议组件的可行性。
- 初期运行在本地 Mac 主机，使用 Caddy、自行编写的反向代理和自建 PostgreSQL；
  issuer 需要可配置，本地集群候选地址为 `https://authx.s`。正式生产
  issuer 和客户端证书信任方式仍待确认。
- 首个上线范围调整为仅本机试运行；本地证书采用受控本地 CA 签发，
  并由浏览器、插件和服务端客户端信任该 CA。试运行的最终 issuer 和所有
  客户端的域名解析仍待确认；试运行通过不等于已获准对外正式上线。
- 首版需要 refresh token；所有用户必须使用 TOTP MFA。账号禁用或用户撤销
  对客户端的 OIDC 授权后，令牌及所有受影响应用的本地会话必须立即失效；
  这与撤销 developer 角色是不同事件。用户主动退出只要求
  退出当前应用。登录会话最长 24 小时。
- 未绑定 TOTP 的用户须先验证第一因素并完成绑定，才能访问受保护功能；
  设备丢失时使用一次性恢复码，必要时由管理员协助。
- 业务应用对每次受保护请求在线校验授权状态，Authx 不可用时拒绝访问；
  撤销时主动断开受影响的 LiveView、WebSocket 等长连接。
- 本地访问链路为 Caddy 终止 TLS，转发到自写代理，再转发到 Authx；
  Authx 仅供本机可信代理访问，代理删除外部转发头并重新设置。
  PostgreSQL 使用同机 Unix socket，并限制本机访问。
- 这些选择不代表机密客户端认证或持久密钥已经实现；密钥文件的权限、
  挂载、备份、轮换和应急处理仍须在实施前确定。
- 本地 CA 的安全分发与客户端信任配置，以及正式生产环境的网络和数据库
  边界仍待确认；本地 Unix socket 不应直接假定适用于远程数据库。

### 初步实现路径核对

- 当前 OAuth 依赖的授权码兑换明确拒绝客户端凭据。需要评估受维护的扩展、
  替换或经过安全审查的认证适配方案，并确保不能绕过认证；仅修改客户端
  注册或 discovery 不会增加客户端认证。
- 已安装的 AshAuthentication 包含 TOTP 和恢复码策略，可优先评估复用；
  但当前用户资源尚未启用 TOTP，也未强制所有登录路径完成第二因素。
- 当前 demo 应用自行建立本地会话，不能假定撤销 Authx 授权就会终止该
  会话。立即失效需要 Authx 与每个接入应用共同支持在线校验或等效机制，
  并明确状态服务不可用时的行为；离线应用不能承诺该保证。

- [ ] 确定生产环境的 HTTPS issuer、部署平台、TLS 终止位置、可信代理、
  单实例或多实例、数据库和密钥管理方式；预发环境使用独立地址、数据和密钥。
- [ ] 列出首批客户端：应用名称、公开或机密客户端、负责人、精确回调 URI、
  必要 scope 和所需会话时长。浏览器插件按公开客户端设计；如服务端应用要求
  机密客户端认证，先确定可支持该能力的实现，不能仅修改 discovery。
- [ ] 决定首版是否需要 refresh token、主动撤销、禁用账号后即时失效、
  全局注销和 MFA；定义退出 Authx 与退出业务应用的区别及可接受的失效延迟。
  若不支持某项，记录替代措施并确认业务接受。
- [ ] 确定账号注册、邮箱验证、密码及 magic link 策略，生产邮件服务、
  管理员权限与恢复流程。
- [ ] 确定可用性目标、备份恢复目标、上线负责人、安全审查人及回滚授权人。

**验收：** 范围和所有待定项有明确结论；列出首批客户端和上线阻塞项。
不能满足业务安全要求时，先评估成熟 OIDC Provider，而不是放宽门禁。

## 1. 固定协议边界与生产配置

**依赖：步骤 0。**

- [ ] 根据确认的范围，将生产 OIDC 路由与其他 demo OAuth 路由分离；
  默认关闭，显式构建启用。禁止把 dev 路由、调试功能和开发默认凭据带入生产。
- [ ] 增加生产配置读取与启动校验：固定 HTTPS issuer、UserInfo resource
  URL、OAuth access token/consent 签名密钥、Phoenix 和用户认证密钥。
  区分现有配置键与新增环境变量，配置缺失或格式错误时启动失败。
- [ ] 校验 issuer 与 discovery 的 issuer、端点 URL 和令牌 `iss` 完全一致；
  生产客户端回调按批准的类型和 URI 策略验证，不能直接沿用 localhost demo。
- [ ] 正式生产保持动态注册和 CIMD 关闭，除非另行设计、审查并测试后启用；
  本地动态注册的受限模式见 [OIDC 客户端管理](oidc-client-management.md)。

**验收：** 缺失或不安全配置的生产构建不能启动；未启用时 OIDC 路由不可用；
启用后只暴露批准的端点。为上述正反情况增加自动化测试。

## 2. 持久密钥与轮换

**依赖：步骤 0；步骤 1 的配置接口须与本步骤协调。**

- [ ] 替换进程启动时生成的 ID Token 私钥，使用步骤 0 选定的密钥管理方式。
  私钥不进入仓库、镜像、日志或 JWKS；所有实例使用一致的活动签名密钥。
- [ ] 实现稳定 `kid` 和 JWKS 多公钥发布。正常轮换时先发布新公钥，
  等待客户端 JWKS 缓存刷新，再切换签名；保留旧公钥直到旧令牌最大有效期、
  时钟偏差和客户端缓存策略允许安全移除。
- [ ] 为 access token/consent 对称密钥分别制定存储、备份、轮换和影响评估；
  不要假定 JWKS 可以验证或轮换 HS256 access token。
- [ ] 制定密钥泄露应急流程：停止使用泄露密钥、必要时立即移除公钥或更换
  对称密钥，并明确因此造成的令牌失效和用户重新登录。

**验收：** 重启和跨实例签发、验签均成功；轮换前、中、后新旧有效令牌
符合预期；私钥不会出现在 JWKS 或日志。测试密钥缺失和错误时的失败行为。

## 3. 客户端与协议安全

**依赖：步骤 0、1、2。**

- [ ] 实现受权限控制的客户端注册、变更、停用与审计；校验客户端类型、
  精确回调 URI、grant、response type 和 scope。禁止把开发注册任务作为生产
  管理接口；验证手动注册路径也执行必要校验。
- [ ] 保留 authorization code + S256 PKCE、短期一次性授权码、nonce、
  scope 和 client/redirect 绑定。针对客户端实现验证 `state`、nonce、
  issuer、audience、签名和过期时间；用户身份以 `(issuer, sub)` 关联，
  不按 email 自动合并。
- [ ] 若步骤 0 要求机密客户端认证，评估并实现或替换为支持所选方式的
  协议组件，同时保留 PKCE；凭据安全存储、轮换和撤销须一并交付。
- [ ] 为并发兑换、授权码重放、错误 verifier、回调不匹配、错误 issuer/
  audience、scope 越权、错误签名、过期令牌及客户端停用增加负向测试。
  用独立客户端与 OIDC 标准兼容性测试验证 discovery 和实际行为一致。

**验收：** 首批客户端成功登录；上述拒绝场景和并发单次消费测试通过；
协议支持范围与 discovery 一致，安全审查无未接受的阻塞问题。

## 4. 会话、撤销与账号安全

**依赖：步骤 0、3。**

- [ ] 按步骤 0 落实 token 和会话时长、客户端登出、Authx 登出、同意撤销、
  账号禁用和密码修改后的行为；明确已签发 access token 的最迟失效时间。
  不得把删除 consent 或 Authx 会话当作已签发令牌立即失效。
- [ ] 为账号禁用和授权撤销落实已确认的立即失效要求：设计资源服务的
  在线状态校验或等效机制，并确定各客户端如何立即终止已建立的本地会话。
  单靠客户端离线验证 JWT 或缩短有效期不能保证立即失效。用户主动退出
  当前应用与账号禁用/授权撤销的传播语义分别测试。
- [ ] 定义在线状态校验的认证、授权、故障和扩展接口，接入应用的受保护请求
  校验失败或 Authx 不可用时拒绝访问；撤销时主动断开相关长连接，并防止
  事件投递失败或重连绕过撤销。明确撤销提交与正在执行请求的边界。
- [ ] 如果需要 refresh token，实现安全存储、轮换、重放检测和撤销，并
  测试并发和泄露场景；不需要则不发布或宣称支持该能力。
- [ ] 为所有用户实现必需的 TOTP 注册、验证、恢复和重置流程，保护种子，
  防止验证码重放并限制验证尝试；覆盖首次注册、设备丢失和管理员恢复。
- [ ] 配置生产邮件投递，测试确认邮箱、密码重置和 magic link；按确认的
  策略落实管理员保护、MFA 和账号恢复。
- [ ] 验证 Cookie 的 `Secure`、`HttpOnly`、`SameSite`、会话轮换与 CSRF
  防护；禁止记录授权码、token、密码、magic link 和私钥。

**验收：** 每项已承诺的退出、撤销和账号变更行为均有端到端测试，失效时间
符合步骤 0 的约定；未实现的能力明确不向客户端承诺。

## 5. 运维、防滥用与预发演练

**依赖：步骤 1–4。**

- [ ] 配置 TLS、HSTS 和可信代理边界，防止客户端伪造转发头；校验应用、
  数据库和密钥管理之间的传输与访问控制。确认代理每一跳均不可被绕过，
  且只有可信来源能提供转发头；验证 Unix socket 权限和数据库访问控制，
  未来采用网络数据库连接时再配置 TLS 和证书校验。
- [ ] 对登录、授权、token 和其他实际公开的无认证端点实施限流与防滥用；
  多实例时限流策略须跨实例生效，并有告警和故障处理方案。
- [ ] 建立脱敏的安全审计、指标和告警，覆盖登录失败、兑换失败、限流、
  密钥变更、客户端管理、服务及数据库异常；限定访问权限和保留期限。
- [ ] 配置生产数据库迁移、备份与恢复；在隔离环境实际演练恢复、应用
  重启、实例故障及密钥轮换，确认达到步骤 0 的目标。
- [ ] 使用独立预发环境和真实部署拓扑完成端到端、负载、故障及安全测试；
  安排独立安全审查，记录并关闭阻塞问题。

**验收：** 预发演练和审查结果可追溯；告警可触发、备份可恢复、部署和
回滚步骤已验证。代码变更执行根目录 `mix precommit`；如修改 demo，
还须在 `demo/` 执行其 `mix precommit`。

## 6. 生产发布与回滚

**依赖：步骤 0–5 的全部门禁通过，且获得上线批准。**

1. 确认生产证书、配置、密钥、数据库备份、迁移及回滚方案，登记发布版本
   和负责人。使用已验证的生产构建，不执行 `mix dev.seed` 或 demo 注册任务。
2. 先部署并验证数据库迁移和应用健康状态，再按批准范围启用 OIDC；
   核对 discovery、JWKS、HTTPS、限流与告警，只注册首批批准的客户端。
3. 以受控测试账号和首批客户端验证登录、退出、异常请求及重启后的验签；
   观察错误率、延迟和安全告警，通过后逐步扩大流量。
4. 出现阻塞问题时停止放量；按照事先演练的方式关闭入口或回滚应用。
   回滚前确认数据库迁移前后兼容性，禁止盲目回退迁移或覆盖生产数据；
   保持仍需验证的签名公钥，必要时执行密钥泄露应急流程。

**最终验收：** 所有门禁、审批、演练和首批客户端验证均有记录，监控正常，
回滚负责人可执行已验证的方案。
